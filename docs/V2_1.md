# V2.1 — relationships first, flow stays local

> **Current project reference — [V2: five designs](https://austinwerner-kai.github.io/future-mobile-design-simplex-chat/v2.html).** V2.1 is the next exploration, not a replacement approved through research.

[Open the V2.1 prototype](https://austinwerner-kai.github.io/future-mobile-design-simplex-chat/v21.html) · [Full-screen mobile](https://austinwerner-kai.github.io/future-mobile-design-simplex-chat/v21.html?mobile=1).

Started 4 October 2026. Independent community design hypothesis for the future mobile SimpleX experience. Original design and fictional fixtures; no official SimpleX release commitment.

## The question

Can people find and return to their relationships more easily when the interface starts with people and entities rather than communication categories?

The proposed audience is people managing personal relationships, small groups, subscriptions and provider correspondence. The immediate deliverable is a working mobile-web exploration for designers to critique. User research and engineering feasibility are not yet established.

## What changed from V2

The home now organises people, groups, publications and providers in one personal world. Favourites are user-selected, and recent activity uses the same entities. There are no top-level Private / Channels / Email filters. Chat and email can sit within a provider relationship, with separate drafts and explicit audiences. A grid and a list are available for comparison. Places remain a future question; the first build does not implement them.

The white canvas, neutral lettering, subtle blue materials and clay actions continue the accepted direction. Pale oat distinguishes provider/email contexts; shape and text labels carry meaning alongside colour. No blue text is used.

## Human structure; octopus flow architecture

Human relationships determine the entities and their meaning. The [octopus theory](EVOLUTION_FROM_ANATOMY.md#the-octopus-theory-is-the-architecture-of-the-flow) informs coordination, local actions, adaptable space, retained context, deliberate crossing and return. It does not require a radial menu.

This build expresses the rules as a home that coordinates, a named relationship workspace, local tools, retained in-page drafts, an exact-content email-to-Maya review and a return to the prior home search/scroll context. It opens a relationship as a focused workspace rather than expanding every tile into the grid. This is a deliberate comparison with the earlier inline experiment, not proof that one approach is better.

## First iteration scope

| Task | Implemented simulation | Limits |
|---|---|---|
| Home | Six selectable favourites, grid/list comparison, seven-entity recent list and name/type search | Static unread counts and activity order; no scaled inbox, manual ordering or profile switching |
| Person | Conversation, separate private proposal, security explanation, reply draft and simulated send | No real network or cryptographic code |
| Group | Member conversation, local proposal and sample membership information | No join/leave or observer lifecycle in V2.1 yet |
| Publication | Public reading with an explicit audience and no private reply composer | Static sample post; no comments or subscription management |
| Provider | Chat/email within one entity, separate drafts, source addresses and recipient labels | Illustrative sample booking content; no mailbox, real provider account or staff permissions |
| Cross-context detail | Edit privately → review text/audience → simulate share with Maya → return to Maya draft | Exact selected text only; no automatic affiliations or forwarding of the original email |
| Favourites | Choose up to six, add/remove in relationship, dialog cancellation and Escape dismissal | Page-session choices; sample directory order; no drag reordering |
| Connection | Same-page dialog, identity choice, demo QR, pending, revoke and acceptance | No real identity verification, camera access or new contact creation |

**Retention:** drafts, favourite choices and simulated actions live in memory only. Reload/new page resets them. No localStorage, sessionStorage or backend is added by V2.1. Interruption recovery and attachment handling remain open work.

**Mobile implementation:** controls are semantic HTML; the app has a scrollable content region and a separate composer. Browser history restores the selected entity; home search and scroll survive local navigation. Desktop presents the rationale beside the mobile study; full-screen mode fills the browser viewport. Native safe-area environment values are supported where the browser supplies them. Real software-keyboard behavior remains untested.

## Storyboard for review

1. Find Maya in the favourites grid or search.
2. Write an unsent reply and open Proposal. The reply stays in the relationship.
3. Share a proposal snapshot. An unchanged version cannot be shared again through that action.
4. Return home and open Harbour Café.
5. Switch between staff chat and email; each retains its own draft.
6. Prepare a booking detail, inspect the exact text and Maya audience, then share deliberately.
7. Open Maya: the selected detail appears and her unsent reply remains.
8. Return home, change favourites, compare list/grid, or prepare an invitation without leaving the page.

## Verification and next questions

[Browser check record and screenshot hashes](v21-browser-check.json) records 25 assertions and ten captures of the local generated build. Checked search/empty state, grid/list, draft isolation/retention, proposal duplicate prevention, sharing cancellation, email-to-chat handoff, publication composer absence, group audience, favourite changes, pending identity freeze, invitation revoke, Escape dismissal, preview concealment, browser Back and reset. Inspected 360, 390 and 768 CSS-pixel widths for document overflow; captured desktop at 1440.

This is agent-operated Chrome simulation, not participant research, physical-phone testing, accessibility certification or protocol validation. The browser checks do not establish screen-reader, enlarged-text or keyboard performance. The screenshots are static evidence of fixture states; they cannot establish human comprehension.

Next: compare grid/list with unfamiliar designers, test on real phones with keyboards and larger text, clarify provider identities and permissions, design groups/profiles/attachments/recovery, and test long names and larger collections. Avoid adding more entity categories until their tasks are useful and understandable.
